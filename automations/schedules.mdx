Schedules fire agent runs on a cron rhythm — a morning digest, a nightly dependency check, a weekly report. Scheduled runs are ordinary [runs](/agents/runs) with a cron for a caller. In the dashboard they live under **Automations → Schedules**.

## Create a schedule

```bash
zwrm schedules create "Morning digest" \
  --agent support-bot \
  --cron "0 9 * * 1-5" \
  --prompt "Summarize overnight tickets" \
  --session-key morning-digest
```

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--agent` | string | — | Agent to run, by ID or name (required) |
| `--cron` | string | — | Standard 5-field cron in **UTC**, `CRON_TZ=<zone>` in front for a time zone, or `@hourly` / `@daily` / `@weekly` / `@monthly` (required) |
| `--prompt` | string | — | The prompt for each run (required) |
| `--session-key` | string | — | Workspace continuity key (blank = fresh workspace per run) |
| `--metadata` | list | — | Tag the schedule with `key=value` (repeatable) |
| `--paused` | bool | `false` | Create the schedule disabled |

- Cron is interpreted in **UTC** unless it starts with a time zone: `CRON_TZ=Europe/Berlin 0 9 * * 1-5` runs at 9:00 Berlin time in summer and in winter. On the night the clocks change, a time in the skipped hour doesn't fire and one in the repeated hour fires twice. Minimum granularity is one minute; seconds fields and `@every` are not supported.
- With a `--session-key`, every firing continues the same workspace — same conversation, same files. Without one, each firing is a one-shot run.
- The agent binding is immutable. Everything else can be [changed in place](#change-a-schedule).
- Up to **20 shared schedules per agent**, plus 20 private ones per member per agent; prompts up to 16 KiB.

## Private and shared schedules

Every member can create schedules on any agent they can use. A schedule belongs to the member who created it, and it fires as them.

A new schedule is **private** to you unless you share it: pass `--share` (`"visibility": "org"` in the API), or point `--session-key` at a shared chat, which makes it shared. A schedule on your [private agent](/agents/overview) is always private.

```bash
zwrm schedules create "Weekend ideas" --agent concierge --cron "CRON_TZ=Europe/Berlin 0 8 * * 4" \
  --prompt "Send me ideas for the weekend" --session-key my-chat     # private to you
zwrm schedules share <schedule-id>      # share it with the organization
zwrm schedules unshare <schedule-id>    # private to you again
```

Each agent holds up to **20 shared schedules**, and each member up to **20 private schedules** per agent. An agent working in a shared chat makes shared schedules, and needs its creator to be a builder; one in your private chat makes yours.

| | Private | Shared |
|---|---|---|
| Its owner | Sees, changes, pauses, deletes and shares it, and reads its runs | The same, and takes it back |
| Other members | Don't see it or its runs | See it and its runs |
| Builders | Don't see it | Also change and pause it |
| Org admins | See it and its runs, pause and delete it, but don't change it | Also take it back and delete it |

- **Its runs stay private too.** A private schedule's runs go only into its owner's own private chats. When one has to be made (a new key, or a fresh workspace per firing), it is the owner's private one. Other members don't find its runs in run lists, the Automations calendar or webhooks, and webhooks for them carry `private: true` and no summary.
- **Runs go where the schedule says.** A private schedule never runs in a shared chat, and a shared one never runs in a private chat. If its chat is shared or taken private later, the schedule is paused, with the reason in its firing log; point it at the right chat and resume it.
- **Only your own chat.** A `--session-key` that names another member's private chat is refused (`409`), and so is a shared chat on your private agent.
- **Sharing takes a shared chat.** A schedule keyed to your private chat can't be shared as it is: share it with a shared chat's key, or none (`zwrm schedules update <id> --session-key team --visibility org`).
- **Changing the key changes who sees it, and that is the owner's call.** Pointing a schedule at a shared chat would make it shared, and pointing it at your private chat would make it private, so such an edit has to say so (`--visibility`, or `visibility` in the API), or it is refused (`409`). Only the schedule's owner can make that change. An edit that keeps the same key, or moves it to a key no chat has yet, keeps it as it was.
- **A private schedule runs only on what its owner wrote.** It runs as you, in your own chats, with your own keys and connections, so it runs only on a prompt, cron and key you wrote or last saved. If someone else changed what a shared schedule does, it pauses when it becomes private (you unshare it, an admin takes it back, or its agent becomes private), and resuming it takes saving its prompt again: review it, then save. `zwrm schedules update <id> --prompt "<the prompt>"` does it too.
- **An admin's take-back pauses it.** An org admin can take a member's shared schedule back, on its own, without other changes; it is then paused, for its owner to look at what others last wrote in it before resuming it. It resumes only once its key fits: a chat of the owner's own, or none.
- **Agents.** An agent counts with its creator's role: changing or deleting schedules takes a builder behind it, and an agent never changes who sees one.
- **Sharing a private agent** moves your schedules into its default chat to your own private chat, since the shared agent's default chat is everyone's.

`zwrm schedules list` shows a `SHARED` and a `MINE` column; the API returns `owner_user_id`, `visibility` and `mine` on each schedule, and `private` on each run.

## Metadata tags

Schedules carry an opaque `key=value` map you can filter on — useful when something else creates schedules on your behalf and needs to find its own again:

```bash
zwrm schedules create "Weekly report" --agent research --cron "@weekly" \
  --prompt "Compile the weekly report" \
  --metadata creator=alice --metadata team=growth

zwrm schedules list --metadata team=growth
```

Filters are ANDed. Up to 20 entries per schedule; keys up to 64 characters, values up to 256. ZWRM never interprets the contents.

## Overlap behavior

A schedule never stacks runs: if the previous run is still going when the next window arrives, the firing is logged as `skipped_still_running` and the schedule waits for the next window. A run parked on an [escalation](/agents/messaging#escalations) counts as still running — a schedule blocked on a human decision skips visibly rather than piling up.

## Inspect and manage

```bash
zwrm schedules list [--agent support-bot]
zwrm schedules firings <schedule-id> [--limit 50]
zwrm schedules update <schedule-id> [--name <n>] [--cron "<expr>"] [--prompt <text>] [--session-key <key>] [--metadata k=v | --clear-metadata]
zwrm schedules pause <schedule-id>
zwrm schedules resume <schedule-id>
zwrm schedules delete <schedule-id>
```

`list` shows each schedule's cron, enabled state, next run, and last run. The firing log records **every due firing regardless of outcome**: `fired`, `skipped_still_running`, `rejected_budget`, or `error`.

### Change a schedule

`update` changes a schedule in place. Only the flags you pass change; the schedule keeps its ID and firing log, and every field you don't pass:

```bash
zwrm schedules update <schedule-id> --cron "0 9 1 */2 *"
zwrm schedules update <schedule-id> --prompt "Summarize overnight tickets and flag urgent ones"
zwrm schedules update <schedule-id> --session-key ""     # fresh workspace per run
zwrm schedules update <schedule-id> --clear-metadata
```

`--metadata` replaces all tags (repeatable); `--clear-metadata` removes them. Use `update` rather than deleting and recreating a schedule: a recreated schedule gets a new ID and loses its session key, tags, and firing log. Agents are told the same, so asking an agent to change a schedule edits it in place.

### Pause and resume

Resuming (or changing the cron) recomputes the next run from now — a long-paused schedule **never catch-up-fires** a backlog.

### Budgets

If the agent's [daily budget](/agents/budgets) is exhausted, firings are logged as `rejected_budget` and skipped; the schedule keeps its rhythm and tries again at the next window.
