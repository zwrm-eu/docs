**Triggers** turn external events into agent runs: Stripe fires on a new order, GitHub on a new issue — and an agent picks it up with the event payload as context. Each trigger is a slug-gated ingestion endpoint with routing, a match gate, a shared secret, and a daily rate cap. In the dashboard they live under **Automations → Triggers** (distinct from **Schedules**, which are time-driven).

## Providers

Every trigger has a **provider** — the kind of event source it ingests. It's fixed when the trigger is created.

| Provider | Source | Created from |
|----------|--------|--------------|
| `webhook` (default) | Any external system that can POST JSON to a URL — including GitHub, GitLab, Stripe, Linear, Shopify, Sentry, and your own systems | CLI, API, dashboard |
| `front` | A [Front AI agent](#front-ai-agent-triggers): teammates' mentions. A mention by a teammate who connected their own Front account is answered with their Front access; others are told how to connect, or, on a trigger that answers everyone, answered with the AI agent's | CLI, API, dashboard (operators) |

All providers feed the same pipeline once a delivery is normalized to a JSON body: **match gate → route → dedup + rate cap → budget-gated run**.

## Create a webhook trigger

```bash
zwrm triggers create "Stripe orders" \
  --default-agent support-bot \
  --instruction "Handle this incoming order event" \
  --session-key-path data.customer.id
```

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--default-agent` | string | — | Catch-all agent (ID or name) when no route matches |
| `--instruction` | string | — | The agent's task for each delivery |
| `--message-template` | string | raw body | Render `{dot.path}` tokens over the body |
| `--session-key-path` | string | — | Dot-path whose value keys session continuity (blank = one-shot) |
| `--match` | JSON | — | Match-condition gate: `[{path,op,value?}]` |
| `--routes` | JSON | — | Routing rules: `[{agent_id,when?}]` |
| `--rate-per-day` | int | `0` | Daily delivery cap (`0` = unlimited) |
| `--no-secret` | bool | `false` | Create a slug-gated trigger with no secret |
| `--secret` | string | — | Import a provider-minted signing secret (Linear, Shopify, Sentry, Front) instead of generating one |

On success the CLI prints the hook URL. When it generates the secret, it also prints the secret — **exactly once** — so store it immediately. An imported `--secret` is never echoed. (`--secret` and `--no-secret` are mutually exclusive.)

## Sending events

```
POST https://<platform>/v1/triggers/hook/<slug>
```

Authenticate each delivery either way:

- `X-Webhook-Secret: <secret>` — the plain secret as a header, or
- `X-Webhook-Signature: sha256=<hex>` — HMAC-SHA256 of the **raw body** with the secret.

### Provider webhooks

Most providers can't send custom headers — they sign with their own fixed header instead. ZWRM recognizes those directly, so you can paste the trigger secret into the provider's webhook settings and it just works:

| Provider | Header | Form |
|----------|--------|------|
| GitHub | `X-Hub-Signature-256` | `sha256=<hex>` |
| GitLab | `X-Gitlab-Token` | Plain secret |
| Bitbucket Cloud | `X-Hub-Signature` | `sha256=<hex>` |
| Gitea / Forgejo | `X-Gitea-Signature` | Bare hex |
| Google Drive / Calendar push | `X-Goog-Channel-Token` | Plain secret |
| Linear | `Linear-Signature` | Bare hex — import the secret with `--secret` |
| Shopify | `X-Shopify-Hmac-Sha256` | Base64 — import the secret with `--secret` |
| Sentry | `Sentry-Hook-Signature` | Bare hex — import the secret with `--secret` |
| Front | `X-Front-Signature` | Base64, signed over `X-Front-Request-Timestamp` and the body — import the secret with `--secret` (see [Front](#front)) |

For GitHub, paste the secret into the webhook's *Secret* field and set the content type to `application/json`. Linear, Shopify, Sentry, and Front mint their **own** signing secret — copy it from the provider and pass it to `--secret` so ZWRM verifies against the same value.

Verification is accept-if-any: an unmatched header never vetoes one that verifies. Apart from Front, providers whose signatures cover a timestamped string (Stripe, Slack, Svix-based) or that require a validation handshake (Microsoft Graph, Event Grid, Zoom) are not supported by header aliasing — send those with an explicit `X-Webhook-Secret`/`X-Webhook-Signature` header.

### Front

For a Front [AI agent](https://dev.frontapp.com/docs/ai-agents), use a [Front AI agent trigger](#front-ai-agent-triggers). A webhook trigger takes Front's [application webhooks](https://dev.frontapp.com/docs/application-webhooks) with no Front-specific option: they need a Front app whose application webhook points at the trigger's hook URL. ZWRM verifies each delivery's signature. When you save an application webhook's URL, Front sends a signed `X-Front-Challenge` request, and ZWRM answers it once the signature verifies. If Front reports that validating the URL failed, the trigger has the wrong secret: it needs Front's **signing secret**, not the client secret. AI-agent deliveries are deduplicated on their `event_id`, since Front can deliver an event more than once. Front's older rule webhooks, signed with HMAC-SHA1, aren't supported.

To connect a Front AI agent, use a [Front AI agent trigger](#front-ai-agent-triggers): it answers each teammate with their own Front access.

Bodies are parsed as JSON (up to 1 MiB). The agent's prompt is built from the trigger's instruction plus the rendered body (via `--message-template`, or the raw body if no template is set).

### Idempotency

Send an `Idempotency-Key` header to make retries safe: a key that was already accepted returns `{"status":"duplicate"}` without dispatching a second run. Front AI-agent deliveries are deduplicated on their signed `event_id` instead.

### Session continuity

Deliveries can share a workspace (conversation + files) with either:

- `--session-key-path data.customer.id` — extract the key from the payload, or
- an `X-Session-Key` header on the request (wins over the path).

Blank = every delivery is a one-shot run on a fresh workspace, deleted about a minute after the run finishes. Its files go with it, so deliver results through the run itself: a reply, a connector, or a callback URL from the payload.

A trigger's keyed workspace is kept for at most **6 hours** after its last delivery, whatever the agent's workspace TTL. After that its volume is reclaimed and the conversation is archived: the next delivery with the same key resumes the conversation on a fresh volume, without the earlier files. A key that already belongs to a chat keeps that chat's TTL.

## Private and shared triggers

Every member can create webhook triggers on any agent they can use. A trigger belongs to the member who created it, and its runs act as them. A [Front AI agent trigger](#front-ai-agent-triggers) is the exception: it always belongs to the organization, only a person with the operator role creates or changes it, and each run acts as the teammate who asked, or, on one that answers everyone, as the AI agent.

A new trigger is **private** to you unless you share it: pass `--share` (`"visibility": "org"` in the API), or share it later. A trigger feeding your [private agent](/agents/overview) is always private.

```bash
zwrm triggers create "Orders" --default-agent support-bot --session-key-path order   # private to you
zwrm triggers share <trigger-id>      # share it with the organization
zwrm triggers unshare <trigger-id>    # private to you again
```

| | Private | Shared |
|---|---|---|
| Its owner | Sees, changes, pauses, deletes and shares it, and reads its events and runs | The same, and takes it back |
| Other members | Don't see it, its events or its runs | See it, its events and its runs |
| Builders | Don't see it | Also change and pause it |
| Org admins | See it, its events and its runs, pause and delete it, but don't change it | Also take it back and delete it |

- **A private trigger's runs are yours.** They act as you, in chats of your own: each event's session key becomes the trigger's own key, so it never lands in another chat of yours or in another member's trigger's chats. The runs are private.
- **A shared trigger's runs go only into shared chats.** An event, or an `X-Session-Key` header, naming a private chat is refused (`422`, logged as `rejected_placement`) instead of running there.
- **A private trigger runs only on what its owner wrote.** If someone else changed what a shared trigger does (its instruction, template, key path, conditions or routing), it pauses when it becomes private, and resuming it takes saving its instruction again. A delivery to such a trigger pauses it too (`rejected_review`).
- **An admin's take-back pauses it**, for its owner to look at before resuming it.
- **Agents** count with their creator's role: creating, changing or deleting triggers takes a builder behind them, and an agent never changes who sees one. An agent working in a shared chat makes the organization's triggers.
- **The GitHub and Notion apps' triggers** stay the organization's, set up from their integration pages. GitHub events are paused and deleted under **Automations** like any trigger.

## Matching and routing

**Match conditions** (`--match`) gate the trigger — every condition must hold or the delivery is ignored (with a `200 ignored` response, so providers stop retrying):

```json
[{"path": "type", "op": "equals", "value": "checkout.session.completed"},
 {"path": "data.object.amount_total", "op": "exists"}]
```

Operators: `exists`, `not_exists`, `equals` (default), `not_equals`, `in`, plus the string operators `contains`, `not_contains`, `starts_with`, `ends_with`. String operators are **case-sensitive** and match only when the payload value is itself a string — a numeric `50` never matches `"50"` — and their `value` must be a non-empty string (max 512 bytes). Like `not_equals`, `not_contains` also passes when the field is missing; pair it with an `exists` condition to require presence. Paths are dot-descent into JSON objects (no array indexing).

**Routes** (`--routes`) pick the agent: the first route whose `when` conditions all match wins; a route with no `when` is a catch-all. If no route matches, the `--default-agent` handles it; with neither, the delivery is dropped.

```json
[{"agent_id": "billing-bot", "when": [{"path": "type", "op": "equals", "value": "invoice.paid"}]},
 {"agent_id": "support-bot"}]
```

The dashboard has a visual editor for conditions and routes.

## Front AI agent triggers

A `front` trigger connects a [Front AI agent](https://dev.frontapp.com/docs/ai-agents) to a ZWRM agent. When a teammate @mentions the AI agent in a Front conversation, the run acts in Front **as that teammate**, with their own Front access, if they are a member who connected their own Front account in ZWRM. A question like "which emails mention this customer?" then searches only what they can see. The answer is posted back to the conversation as an internal comment from the AI agent.

The run works for that teammate **on every connector**, as in a chat they started: each of the agent's other per-user connections acts as their own account too, unless an operator set that connection to always act as the agent.

Only a teammate starts a run: by mentioning the AI agent, or, on a trigger that answers everyone, by assigning a conversation to it. A customer's email never does: a new inbound message on a conversation assigned to the AI agent is ignored.

### Who it answers

By default a Front trigger answers **only members** it recognises as the teammate who asked. Nothing else gets a run:

- a teammate who hasn't connected their own Front account in ZWRM, or isn't a member, gets one short internal comment from the AI agent telling them how to connect, once per mention;
- an assignment to the AI agent starts nothing (it names no person);
- a mention ZWRM can't read the author of starts nothing.

Set the trigger to answer **everyone** (`--front-answers everyone`, or turn off **Answer only members** in the dashboard), and each of these starts a run as the **Front AI agent** itself, with the access you grant it in Front, assignments included. Changing it takes the operator role.

A member whose connected Front account stopped working (revoked or expired) isn't switched to the AI agent: the answer tells them to reconnect.

ZWRM learns who asked from Front itself, never from the event or the model. It reads the comment the event names from the conversation, as the AI agent, and acts as its author only when all of these hold:

- the comment mentions this AI agent;
- its author wrote it in person within the last 10 minutes, at most 5 minutes before Front delivered the event;
- no run has acted on it for this AI agent before (each comment starts at most one run per AI agent);
- exactly one member's Front sign-in is that teammate (ZWRM learns each member's teammate ID when they connect their Front account).

Otherwise ZWRM doesn't know who asked, and the trigger treats them as anyone it doesn't recognise (see above).

A run's prompt carries the trigger's instruction and the event's IDs, not the rest of the event's body, and tells the agent that everything in the conversation is untrusted data: emails come from outside the company, so instructions in them are never followed, and nothing beyond the answer (no secrets, memories or credentials) goes into the reply.

A run that acts for a member runs in that member's private workspace, so its transcript is theirs alone, and they can continue it in Cowork.

<Warning>
On a trigger that answers everyone, the AI agent's own Front access is what **everyone** who can mention it gets. Grant it only the Front workspaces every teammate may see, and start with read and write permissions without send. Answering only members, its own access only reads who asked and posts the answers. Either way, an answer is posted to the conversation, where everyone who can see the conversation can read it, including what the asker's access found. Front conversations are untrusted input to the agent: a customer's email can try to steer it.
</Warning>

### Several Front AI agents

One Front connection serves several Front AI agents, say `@ferdi` and `@heidi`. Each is its own trigger with its own ZWRM agent, and each ZWRM agent acts in Front as its own Front AI agent: it reads and posts as that AI agent. Members sign in to Front once, on the connection, for all of them. A comment that mentions two AI agents is answered by both.

Every ZWRM agent on the Front connection is its own AI agent in Front, one to one: it gets the connection together with its Front AI agent, never before, and no two agents share one. A Front trigger takes no routes: it answers with its own agent. An agent that still has the connection but no Front AI agent of its own (a setup nobody finished) shows **No Front account yet** under **Agents using it** on the Front integration, and its Front calls are refused until it gets one or loses the connection.

### Set it up

You need the operator role, a shared [Front connection](/context/connectors) where members sign in with their own Front accounts, and a shared agent to answer.

In the dashboard, open **Integrations → Front** and choose **Add an agent** under **Agents using it**. The dialog follows Front's own AI agent setup, so keep the two side by side.

1. **Agent.** Pick the agent that answers. Only shared agents can: every member who mentions it uses it.
2. **Events from Front.** In Front, open **Settings → Company → Agents → Create AI agent**. Its first step, **Front → Agent**, shows a **signing secret** next to the **Webhook URL**. Paste the signing secret into the dialog: ZWRM creates the agent's Front trigger and shows its URL. Paste that URL into Front's **Webhook URL** field and send Front's test event. The dialog ticks once the event arrives, and any later signed event from Front, such as a mention, counts too.
3. **Its account in Front.** Front's next step, **Agent → Front**, shows the AI agent's **client ID**, **client secret** and **OAuth URL**, your company's `https://<company>.frontapp.com/oauth/token`. The dialog fills in the OAuth URL from the connection's other AI agents. Front shows the client secret only once. ZWRM checks the credentials with Front before it saves them, and stores nothing when Front refuses them, when they sign in as a person rather than as the AI agent, or when Front won't give the AI agent its MCP tools. Right after you create an AI agent, Front can take a minute or two to accept its credentials.
4. **Tools.** Choose what the agent may do in Front; the dialog starts from read and write. Then finish Front's wizard.
5. Ask each teammate to connect their own Front account under **Integrations → Front**.

Each agent's row under **Agents using it** says what it still lacks, and opens the dialog at that step. **Remove from Front** takes away the agent's Front tools, its Front AI agent's credentials, and its Front trigger with the trigger's instruction. What the trigger does (its instruction, conditions, whom it answers and its daily limit) is still edited under **Automations**.

With the CLI, in the same order:

```bash
# 2. The trigger, with Front's signing secret. Paste the URL it prints into
#    Front's Webhook URL field, then send Front's test event.
zwrm triggers create "Front" \
  --front-connection front \
  --default-agent support-bot \
  --secret <front-signing-secret> \
  --instruction "Answer the teammate's question about this conversation."

# 3. Its account in Front, checked with Front before it is saved.
zwrm mcp upstream agent-credentials front --agent support-bot \
  --client-id <client-id> --client-secret <client-secret> \
  --token-url https://<company>.frontapp.com/oauth/token

# 4. Its tools. Start with reading and commenting, without sending.
zwrm agent tools set support-bot front \
  --tools read_conversation,read_message,search_conversations,list_inboxes,add_comment
```

Then finish Front's wizard, and ask each teammate to connect their own Front account under **Integrations → Front**. The agent's row under **Agents using it** shows the test event once it has arrived (the API's `front.verified_at` on the trigger).

Add `--front-answers everyone` to the trigger to answer people it doesn't recognise, as the AI agent. Until its agent has its Front AI agent's credentials on the connection, a Front trigger answers Front's test event and nothing else.

For another Front AI agent, add another agent the same way, on the same connection. Members don't sign in again.

A Front trigger always belongs to the organization, and its agent must be shared: every member who mentions it uses it. Each agent's Front AI agent has one Front trigger, and removing an agent's Front AI agent (**Remove from Front**, or `agent-credentials --clear`) deletes it. Creating one, and changing what it does, takes a person with the operator role: an agent's credential can't, and a trigger an agent last changed acts as no member, so it answers nobody, or, answering everyone, only as the AI agent. Each Front conversation keeps one workspace per member who asks there, and one shared workspace for everything the AI agent answers. Unassigning the AI agent starts nothing, and doesn't stop a run already going: cancel it with `zwrm agent run cancel <run-id>`.

Only Front's signature is accepted on a Front trigger. Deliveries are deduplicated on their signed `event_id`. If ZWRM can't reach Front in time to learn who asked, it answers `500` and Front delivers the event again.

## Notion mentions

The Notion app lets an agent work in Notion like a teammate. Each agent is a person in your Notion workspace: mention that person in a comment or in a page's text, and the agent reads the page and answers there, as that person.

### Set it up

An admin connects the workspace, and adding agents takes the operator role. Each agent needs its own Notion member account, such as `mako@yourcompany.com`, so it can be mentioned and reply as itself.

1. **Connect Notion.** Under **Integrations → Notion**, an admin chooses **Connect Notion** and picks the workspace and the pages to share with ZWRM. Mentions arrive only from pages shared with ZWRM, and the **Notion workspace** card shows how many it sees. To share more, choose **Choose pages**, or in Notion open a page's **••• → Connections** and add ZWRM.
2. **Add an agent.** Under **Agents using it**, choose **Add an agent** and pick a shared agent, and the workspace if you have several.
3. **Sign in as the agent.** Sign in to Notion as the agent's own account. If your browser is signed in to Notion as yourself, use a private window, or choose **Copy link** in the dialog and send the sign-in link to whoever has the agent's login. ZWRM asks Notion who signed in and links that person, together with the agent's Notion trigger and its Notion tools. It links nothing when the account is a member's own, a bot, not in the workspace, or already linked to another agent there. When ZWRM can't tell who signed in, choose the person by hand.
4. **Tools.** The agent starts with read and write on Notion; narrow it any time.

Each agent's row under **Agents using it** says what it still lacks, such as its sign-in, a sign-in as someone else, or its tools, and opens the dialog at that step. **Remove from Notion** unlinks the agent in every workspace, which removes its trigger, and takes away its Notion tools and its Notion sign-in.

An agent reads a page as its own Notion account, so that account needs access to every page where it's mentioned; mentions only arrive from pages shared with ZWRM. A linked agent's own comments never start a run, and an agent takes part in a thread only by commenting as its linked person.

## GitHub

The GitHub App lets agents work in your repositories like a teammate. Mention the App (`@zwrm-agent`, or write `/zwrm`) in an issue, a pull request or a review, or add the `zwrm` label. The agent answering in that repository then takes it on: it clones the repository, makes and checks the change, opens a pull request, and answers on the thread. To ask a particular agent, start a line with its name and a slash, such as `/ferdinand`. Agents act on GitHub as the App, with short-lived tokens ZWRM mints for the installation.

### Set it up

An admin connects GitHub, and adding agents takes the operator role.

1. **Connect GitHub.** Under **Integrations → GitHub**, an admin chooses **Connect GitHub** and signs in to GitHub. ZWRM finds the installations of the App that the admin owns. A single one connects at once, several are offered to pick from, and with none the admin goes on to install the App. An installation connects only for someone who owns it on GitHub: the account itself, or an owner of the organization. On an organization, a member who isn't an owner can only request the install, and an owner approves it. Choose the App's repositories on GitHub; the card shows how many it reaches.
2. **Add an agent.** Under **Agents using it**, choose **Add an agent** and pick a shared agent.
3. **Where it answers.** Where a mention of the App reaches it:
   - **everywhere else**: in every repository no other agent answers in;
   - **in chosen repositories**: each repository has one answering agent;
   - **only by name**: no mention of the App reaches it, only its own name.
4. **Tools.** The agent starts with read and write on GitHub; narrow it any time.

Each agent's row under **Agents using it** says what it still lacks and opens the dialog at that step. **Remove from GitHub** takes away the agent's answering, its trigger, its GitHub events, its GitHub tools and its git access.

### Asking an agent by name

Every agent under **Agents using it** also answers to its own name with a slash: `/ferdinand`. A one-word display name works, as does the agent's handle; each row under **Agents using it** shows the one to use. Start a line with it, as with any slash command: `/ferdinand can you look at the footer?`. It works in any repository the App reaches, even where another agent answers. Naming several agents, such as `/ferdinand /carla compare notes`, starts a run for each. A name in the middle of a sentence is just text.

`@ferdinand` doesn't work: on GitHub, `@name` is a person's account, and GitHub would notify whoever owns that name.

Once an agent takes a thread on, the thread stays with it. A later `@zwrm-agent` there reaches the same agent, until someone names another one. A pull request an agent opens stays with it too, so comments on it reach the agent that wrote it. The `zwrm` label goes to the agent the thread is with, or the repository's, whatever the issue's text names. Each answer is signed with the agent's name and `/name`. Naming an agent that isn't on GitHub starts nothing, and the App says so once.

### Who may ask

Only people with write access to the repository start a run, and bots never do. Anyone else who mentions the App gets one short comment saying so, once per thread. So does someone asking in a repository where no agent answers. Each answering agent has its own trigger: pause it, or change its daily limit, under **Automations**.

### What the agent does on GitHub

- **👀** marks what it took on.
- **Its answer is posted on the thread** when the run ends, with a link to the run. In a private repository, the files it saved are linked under the answer.
- **When no run starts**, because the trigger is paused, over its daily limit or out of budget, the App says why on the thread.
- **A review is answered once**, with all its inline comments.
- **On its own open pull requests** the agent also hears comments and reviews that ask for changes, without a mention. That is up to 10 a day per pull request, and never from bots. It stays quiet when nothing is asked of it.
- **The `zwrm` label** hands an issue or pull request to the agent, since GitHub doesn't let an App be assigned. ZWRM creates the label in the repositories where agents answer.

Everything written on GitHub is untrusted input to the agent. In a public repository, anyone can read its answers.

### GitHub events

Under **GitHub events** on the GitHub page, an agent does something when something happens on GitHub:

- an **issue is closed** as completed;
- a **pull request is merged**;
- a **release is published**.

Issues and pull requests can be narrowed to a label, and every event to chosen repositories. An event starts a run when someone with write access does it, or when a bot such as a merge queue merges or publishes. An issue closed by a bot, and anything the App itself does, start nothing. The run works in a workspace of its own, and nothing goes back to GitHub unless the task says so. Each event is a trigger: pause or delete it under **Automations**, where **Edit** opens it on the GitHub page. The routines "Tell customers about a fix" and "Release notes" open the form filled in.

### Members' own GitHub

Members can sign in with their own GitHub account under **Accounts** on the GitHub page. In their private chats, an agent then uses GitHub as them, within the App's repositories and their own rights. Shared chats, runs and answers on GitHub act as the App. A private agent has no GitHub account of its own: it works only with its owner's sign-in. Admins choose how agents act in private chats under **Who may use it**: as the person, as the person else the App, or always as the App, which leaves private agents without GitHub.

## Responses

| Status | Meaning |
|--------|---------|
| `200 {"status":"accepted","run_id":…}` | Run dispatched |
| `200 {"status":"ignored"}` | Match conditions not met — stop retrying |
| `200 {"status":"duplicate"}` | Idempotency key already processed |
| `401` | Invalid or missing secret/signature |
| `404` | Unknown or inactive slug — also returned when a matched route's agent is unusable (fail-closed) |
| `422` | The event names a chat this trigger's runs don't go into, or the agent has no shared credential — stop retrying; see the delivery log |
| `409` | Same idempotency key currently in flight — retry shortly |
| `413` | Body over 1 MiB |
| `429` | Daily rate cap or [agent budget](/agents/budgets) exceeded — retry later |
| `503` | Transient dispatch failure — safe to retry |

ZWRM does not retry inbound deliveries itself — the status codes are chosen so the *sender's* retry logic does the right thing.

## Inspect and manage

```bash
zwrm triggers list
zwrm triggers deliveries <trigger-id> [--limit 50]
zwrm triggers update <trigger-id> [--name <n>] [--default-agent <a> | --clear-default-agent] [--instruction <text>] [--message-template <tpl>] [--session-key-path <path>] [--match <json>] [--routes <json>] [--rate-per-day <n>]
zwrm triggers pause <trigger-id>
zwrm triggers resume <trigger-id>
zwrm triggers delete <trigger-id>
```

The delivery log records each delivery's disposition: `accepted`, `ignored`, `rejected_auth`, `rejected_route`, `rejected_rate`, or `rejected_budget`, plus the dispatched run ID. Duplicates are **not** logged — that outcome only returns `{"status":"duplicate"}` to the caller — and transient failures (`503`) record nothing, since the event stays retryable. Because the hook endpoint is public, `rejected_auth` rows are capped at 50 per trigger per 24h. Ignored deliveries record which condition failed and the actual value seen (e.g. `data.type equals 'order' — actual='refund'`).

### Change a trigger

`update` changes a trigger in place. Only the flags you pass change, and the trigger keeps its ID, hook URL, secret, and delivery log:

```bash
zwrm triggers update <trigger-id> --instruction "Refund duplicate charges"
zwrm triggers update <trigger-id> --routes '[{"agent_id":"billing-bot","when":[{"path":"type","op":"equals","value":"charge.refunded"}]}]'
zwrm triggers update <trigger-id> --match ""            # remove the match gate
zwrm triggers update <trigger-id> --clear-default-agent
zwrm triggers update <trigger-id> --rate-per-day 0      # unlimited
```

`--match` and `--routes` replace the whole list, and an empty value removes it; invalid JSON is rejected before anything is sent. The hook URL and secret can't be changed. Use `update` rather than deleting and recreating a trigger: deleting it retires its hook URL, so the sender's deliveries to it fail until you reconfigure the sender with the new trigger's URL and secret, and the delivery log starts empty. Agents are told the same.
