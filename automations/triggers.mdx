**Triggers** turn external events into agent runs: Stripe fires on a new order, GitHub on a new issue, a Teams message arrives — and an agent picks it up with the event payload as context. Each trigger is a slug-gated ingestion endpoint with routing, a match gate, a shared secret, and a daily rate cap. In the dashboard they live under **Automations → Triggers** (distinct from **Schedules**, which are time-driven).

## Providers

Every trigger has a **provider** — the kind of event source it ingests. It's fixed when the trigger is created.

| Provider | Source | Created from |
|----------|--------|--------------|
| `webhook` (default) | Any external system that can POST JSON to a URL — including GitHub, GitLab, Stripe, Linear, Shopify, Sentry, and your own systems | CLI, API, dashboard |
| `msteams` | A Microsoft Teams chat, via a Microsoft Graph change-notification subscription on your connected account | API, dashboard (**not** the CLI) |

Both providers feed the same pipeline once a delivery is normalized to a JSON body: **match gate → route → dedup + rate cap → budget-gated run**.

## Create a webhook trigger

```bash
zwrm triggers create "Stripe orders" \
  --default-agent support-bot \
  --instruction "Handle this incoming order event" \
  --session-key-path data.customer.id
```

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--default-agent` | string | — | Catch-all agent (ID or name) when no route matches |
| `--instruction` | string | — | The agent's task for each delivery |
| `--message-template` | string | raw body | Render `{dot.path}` tokens over the body |
| `--session-key-path` | string | — | Dot-path whose value keys session continuity (blank = one-shot) |
| `--match` | JSON | — | Match-condition gate: `[{path,op,value?}]` |
| `--routes` | JSON | — | Routing rules: `[{agent_id,when?}]` |
| `--rate-per-day` | int | `0` | Daily delivery cap (`0` = unlimited) |
| `--no-secret` | bool | `false` | Create a slug-gated trigger with no secret |
| `--secret` | string | — | Import a provider-minted signing secret (Linear, Shopify, Sentry) instead of generating one |

On success the CLI prints the hook URL and — **exactly once** — the secret. Store it immediately. (`--secret` and `--no-secret` are mutually exclusive.)

## Sending events

```
POST https://<platform>/v1/triggers/hook/<slug>
```

Authenticate each delivery either way:

- `X-Webhook-Secret: <secret>` — the plain secret as a header, or
- `X-Webhook-Signature: sha256=<hex>` — HMAC-SHA256 of the **raw body** with the secret.

### Provider webhooks

Most providers can't send custom headers — they sign with their own fixed header instead. ZWRM recognizes those directly, so you can paste the trigger secret into the provider's webhook settings and it just works:

| Provider | Header | Form |
|----------|--------|------|
| GitHub | `X-Hub-Signature-256` | `sha256=<hex>` |
| GitLab | `X-Gitlab-Token` | Plain secret |
| Bitbucket Cloud | `X-Hub-Signature` | `sha256=<hex>` |
| Gitea / Forgejo | `X-Gitea-Signature` | Bare hex |
| Google Drive / Calendar push | `X-Goog-Channel-Token` | Plain secret |
| Linear | `Linear-Signature` | Bare hex — import the secret with `--secret` |
| Shopify | `X-Shopify-Hmac-Sha256` | Base64 — import the secret with `--secret` |
| Sentry | `Sentry-Hook-Signature` | Bare hex — import the secret with `--secret` |

For GitHub, paste the secret into the webhook's *Secret* field and set the content type to `application/json`. Linear, Shopify, and Sentry mint their **own** signing secret — copy it from the provider and pass it to `--secret` so ZWRM verifies against the same value.

Verification is accept-if-any: an unmatched header never vetoes one that verifies. Providers whose signatures cover a timestamped string (Stripe, Slack, Svix-based) or that require a validation handshake (Microsoft Graph, Event Grid, Zoom) are not supported by header aliasing — send those with an explicit `X-Webhook-Secret`/`X-Webhook-Signature` header, or use the `msteams` provider for Teams.

Bodies are parsed as JSON (up to 1 MiB). The agent's prompt is built from the trigger's instruction plus the rendered body (via `--message-template`, or the raw body if no template is set).

### Idempotency

Send an `Idempotency-Key` header to make retries safe: a key that was already accepted returns `{"status":"duplicate"}` without dispatching a second run.

### Session continuity

Deliveries can share a workspace (conversation + files) with either:

- `--session-key-path data.customer.id` — extract the key from the payload, or
- an `X-Session-Key` header on the request (wins over the path).

Blank = every delivery is a one-shot run on a fresh workspace.

## Matching and routing

**Match conditions** (`--match`) gate the trigger — every condition must hold or the delivery is ignored (with a `200 ignored` response, so providers stop retrying):

```json
[{"path": "type", "op": "equals", "value": "checkout.session.completed"},
 {"path": "data.object.amount_total", "op": "exists"}]
```

Operators: `exists`, `not_exists`, `equals` (default), `not_equals`, `in`. Paths are dot-descent into JSON objects (no array indexing).

**Routes** (`--routes`) pick the agent: the first route whose `when` conditions all match wins; a route with no `when` is a catch-all. If no route matches, the `--default-agent` handles it; with neither, the delivery is dropped.

```json
[{"agent_id": "billing-bot", "when": [{"path": "type", "op": "equals", "value": "invoice.paid"}]},
 {"agent_id": "support-bot"}]
```

The dashboard has a visual editor for conditions and routes.

## Microsoft Teams triggers

An `msteams` trigger wakes an agent on messages in a Teams chat — and, uniquely, gives the agent a way to reply. Because it rides a Microsoft Graph subscription on your connected account, it's created from the **dashboard or API only**, not the CLI.

**Prerequisites:** the org has a [Microsoft 365 connector](/context/shared-connectors) (a per-user OAuth MCP upstream), and the user creating the trigger has connected their Microsoft account to it. The trigger uses that delegated grant (Chat.Read; presence needs Presence.ReadWrite).

**Configuration:**

| Field | Description |
|-------|-------------|
| `upstream` | The Microsoft 365 connector name (immutable — changing it means a new trigger) |
| `include_own_messages` | `false` (default) fires only on received messages; `true` also fires on your own outgoing messages |
| `presence` | Publish "Available" presence for the connected account while the trigger is active |

Each delivery defaults to one persistent session per chat (`session_key_path` = `chat_id`), so the agent keeps context across a conversation. The run prompt carries a **reply preamble**: it tells the agent this came from a Teams message and that the only way to reply is a Microsoft 365 connector tool posting back to the originating `chat_id`. The agent replies **through the connector** — there is no built-in messaging (see [Waiting & outputs](/agents/messaging)).

ZWRM manages the Graph subscription for you (create on activate, renew before its ~70h expiry, drop on delete). Subscription health surfaces read-only as `subscription_active`, `subscription_expires_at`, and any `last_error` / `presence_error`.

## Responses

| Status | Meaning |
|--------|---------|
| `200 {"status":"accepted","run_id":…}` | Run dispatched |
| `200 {"status":"ignored"}` | Match conditions not met — stop retrying |
| `200 {"status":"duplicate"}` | Idempotency key already processed |
| `409` | Same idempotency key currently in flight — retry shortly |
| `413` | Body over 1 MiB |
| `429` | Daily rate cap or [agent budget](/agents/budgets) exceeded — retry later |
| `503` | Transient dispatch failure — safe to retry |

ZWRM does not retry inbound deliveries itself — the status codes are chosen so the *sender's* retry logic does the right thing. (Teams deliveries that hit the rate cap or budget are acknowledged `2xx` so Graph doesn't redeliver the whole batch.)

## Inspect and manage

```bash
zwrm triggers list
zwrm triggers deliveries <trigger-id> [--limit 50]
zwrm triggers pause <trigger-id>
zwrm triggers resume <trigger-id>
zwrm triggers delete <trigger-id>
```

The delivery log records every delivery with its disposition: `accepted`, `duplicate`, `ignored`, `rejected_route`, `rejected_rate`, or `rejected_budget`, plus the dispatched run ID.
