Templates are the base images that sandboxes boot from. Each template is a Docker-to-ext4 converted filesystem image containing an operating system, language runtime, tools, and default configuration. ZWRM ships with built-in templates and supports custom templates.

## Built-in templates

These templates are registered automatically when the control plane starts, from Dockerfiles embedded in the `zwrmd` binary. They are registered with status `pending` — the actual image build is triggered on first use or via `zwrm templates rebuild`:

| Template | Description |
|----------|-------------|
| `base` | Ubuntu with git, curl, build-essential, and common dev utilities |
| `python` | Python 3.12 + pip + venv on the base image |
| `node` | Node.js 22 + npm + yarn + pnpm on the base image |

## Template lifecycle

1. **Pending** — Template record created in database
2. **Building** — Docker image is being built and converted to ext4
3. **Ready** — Image is built and available for sandbox creation
4. **Failed** — Build failed (error stored in `build_error` field)

## Creating custom templates

Custom templates are built from a Docker build context: a Dockerfile plus any local files it copies in. The Dockerfile defines the complete environment — OS packages, language runtimes, tools, and default configuration — and `COPY`/`ADD` pull in assets from the uploaded context (the current directory by default, `--context <dir>` otherwise, `.dockerignore` applied, up to 1 GiB compressed).

<Tabs>
  <Tab title="CLI">
    ```bash
    zwrm templates create my-ml --dockerfile ./Dockerfile
    ```

    The build runs asynchronously. Check progress with:
    ```bash
    zwrm templates list
    ```

    To set a default egress policy for all sandboxes created from this template:
    ```bash
    zwrm templates create my-ml --dockerfile ./Dockerfile \
      --egress-mode deny_all \
      --egress-allow-cidr 140.82.112.0/20 \
      --egress-allow-port 443
    ```

    Egress flags:
    - `--egress-mode` — `allow_all` or `deny_all` default for sandboxes from this template
    - `--egress-allow-cidr CIDR` — Default allowed outbound CIDR (repeatable; implies `deny_all`)
    - `--egress-deny-cidr CIDR` — Default denied outbound CIDR (repeatable)
    - `--egress-allow-port PORT` — Default TCP port restriction for `--egress-allow-cidr` (repeatable)

    <Warning>
    In `deny_all` mode, allowed destinations must be enumerated explicitly. An `allow_cidr` that overlaps the VM subnet — including `0.0.0.0/0` — is rejected when a sandbox is created, because it would punch a hole in cross-app isolation. See [Egress controls](/sandboxes/egress).
    </Warning>

    Quota flags:
    - `--disk-size-mb MIB` — Writable disk quota for sandboxes from this template (256–65536 MiB; default 2048)
    - `--bandwidth-mbps N` — Default per-drive bandwidth cap (MiB/s)
    - `--ops-per-sec N` — Default per-drive IOPS cap
    - `--burst-mbps N` — Default one-time bandwidth burst (MiB)
    - `--burst-ops N` — Default one-time ops burst
  </Tab>
  <Tab title="API">
    ```bash
    curl -X POST http://localhost:8080/v1/templates \
      -H "Content-Type: application/json" \
      -d '{
        "name": "my-ml",
        "dockerfile": "FROM ubuntu:22.04\nRUN apt-get update && apt-get install -y python3 python3-pip\nRUN pip3 install numpy pandas scikit-learn\n",
        "description": "Machine learning template",
        "env": {
          "PYTHONUNBUFFERED": "1"
        },
        "egress": {
          "mode": "deny_all",
          "allow_cidrs": ["140.82.112.0/20"],
          "allow_ports": [443]
        },
        "disk_size_mb": 8192,
        "rate_limit": {
          "bandwidth_mbps": 200,
          "ops_per_sec": 8000
        }
      }'
    ```

    Body fields beyond `name` and `dockerfile`:
    - `description` (string) — Human-readable description
    - `env` (object) — Default environment variables for sandboxes from this template
    - `egress` (object) — Default egress policy (see [Egress controls](/sandboxes/egress))
    - `disk_size_mb` (integer) — Writable disk quota in MiB for sandboxes from this template (256–65536; unset uses the server default of 2048)
    - `rate_limit` (object) — Default Firecracker drive caps: `bandwidth_mbps`, `ops_per_sec`, `burst_mbps`, `burst_ops` (all optional; zero means unlimited for that dimension)
  </Tab>
</Tabs>

### Updating disk and rate-limit quotas

A template's disk quota and drive rate limit can be changed without rebuilding the image:

<Tabs>
  <Tab title="CLI">
    ```bash
    zwrm templates update-quota my-ml --disk-size-mb 8192
    zwrm templates update-quota my-ml --bandwidth-mbps 200 --ops-per-sec 8000
    zwrm templates update-quota my-ml --clear-rate-limit
    ```

    `--clear-rate-limit` drops the per-template rate limit and falls back to the size preset's default.
  </Tab>
  <Tab title="API">
    ```bash
    curl -X PATCH http://localhost:8080/v1/templates/my-ml/quota \
      -H "Content-Type: application/json" \
      -d '{
        "disk_size_mb": 8192,
        "rate_limit": {"bandwidth_mbps": 200, "ops_per_sec": 8000}
      }'
    ```

    Send `"clear_rate_limit": true` to delete the per-template rate limit (falling back to preset defaults) — a JSON `null` for `rate_limit` is indistinguishable from omitting the field.
  </Tab>
</Tabs>

Changes apply to sandboxes created after the update; a per-sandbox `disk_size_mb` or `rate_limit` on the create request still overrides the template default.

### Template metadata

Templates can include a `zwrm-template.toml` file in their repository root with metadata. All fields must live under the `[template]` table — top-level keys are ignored:

```toml
[template]
name = "my-ml"
description = "Machine learning environment"
author = "your-org"
icon = "brain"
tags = ["python", "ml", "data-science"]
default_size = "performance-2x"
min_size = "shared-cpu-4x"

[template.env]
PYTHONUNBUFFERED = "1"
OMP_NUM_THREADS = "2"
```

## Build pipeline

The template build pipeline converts a Dockerfile into a Firecracker-bootable ext4 filesystem:

1. **Docker build** — Standard `docker build` using the provided Dockerfile
2. **Container export** — Export the built image as a tar archive
3. **ext4 creation** — Create an ext4 filesystem and extract the tar contents into it
4. **Init injection** — Inject init scripts for VM boot (networking, overlayfs setup)
5. **Daemon injection** — Install `zwrm-sandboxd`, the in-VM agent daemon that the host communicates with for command execution and file operations
6. **Agent skeleton** — Copy `/home/agent` to `/etc/skel/agent-skel/` for user provisioning
7. **Cache** — Store the result with a content-addressed cache key

After a template image is built, the control plane captures a **base snapshot** in the background: a self-contained Firecracker snapshot of one clean, booted VM from the template. Subsequent sandbox creates resume from it instead of cold-booting. Capture is best-effort — if it fails, sandboxes from the template simply cold-boot until the next build refreshes the snapshot. See [Fast creation](/sandboxes/warm-pool).

<Info>
Build caching is content-addressed. The cache key includes the repository URL and commit hash. Rebuilding with no upstream changes is a no-op.
</Info>

## Rebuilding templates

When you update a template's Dockerfile, rebuild it to create a new version:

<Tabs>
  <Tab title="CLI">
    ```bash
    zwrm templates rebuild my-ml
    ```
  </Tab>
  <Tab title="API">
    ```bash
    curl -X POST http://localhost:8080/v1/templates/my-ml/rebuild
    ```
  </Tab>
</Tabs>

Rebuilding increments the template version and triggers a new build. The version bump invalidates the template's base snapshot (its fingerprint no longer matches), so new sandboxes cold-boot until a fresh base snapshot is captured after the rebuild completes. Existing sandboxes continue using their current image — only new sandboxes use the updated template.

</Warning>

## Template resolution

When creating a sandbox, the `template` field is resolved in this order:

1. **By ID** — Exact match on template ID (e.g., `tmpl_abc123`)
2. **By name (org-scoped)** — Match on name within the requesting organization's custom templates
3. **By name (built-in)** — Match on name among built-in templates

This means custom templates with the same name as a built-in template take precedence for that organization.
