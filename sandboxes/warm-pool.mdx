ZWRM accelerates sandbox creation with **per-template base snapshots**. The first sandbox created from a template cold-boots a fresh VM (~2-3 seconds). In the background, the control plane captures a base snapshot of a clean, booted VM for that template — later creates resume from that snapshot instead of booting from scratch, targeting sub-500ms creation.

<Note>
Earlier versions of ZWRM used a warm pool of pre-booted VMs. The warm pool has been removed: the `[sandboxes.warm_pool]` config keys are silently ignored, and the `zwrm sandbox pool` command and `GET /v1/sandboxes/pool` endpoint no longer exist. Base-snapshot resume replaces it without holding idle VMs.
</Note>

## How it works

1. **Capture** — After a template build completes, the control plane boots one throwaway VM from the template image in the background. The producer VM always uses the smallest preset (`shared-cpu-1x`) — the snapshot only needs to capture a clean, quiesced VM. The guest is parked at a pre-daemon barrier, then suspended into a self-contained snapshot (VM state + memory + writable overlay).

2. **Store** — The snapshot is stored on the host that produced it, under `/var/lib/zwrm/template-snapshots/<template-id>`, and recorded against the template together with a fingerprint of the template version, image reference, and baked init script.

3. **Resume** — When a sandbox is created and the template has a current base snapshot, the new VM resumes from it on the snapshot's host. The sandbox gets a fresh identity — IP address, machine ID, and daemon token — applied before the in-VM daemon starts.

4. **Fallback** — Resume is strictly best-effort. If it fails for any reason (for example, the snapshot's host is unreachable), sandbox creation transparently falls back to a cold boot.

## Latency

| Path | Typical latency |
|------|----------------|
| Base-snapshot resume | < 500ms |
| Cold boot | 2-3 seconds |

## Snapshot invalidation

Each base snapshot is keyed to a fingerprint of the template version and image reference. Rebuilding a template bumps its version, so the existing snapshot no longer matches — sandboxes cold-boot until a fresh base snapshot is captured after the rebuild finishes. Capture is automatic; no operator action is required.

## When creates cold-boot

A sandbox creation falls back to a cold boot when:

- The template has no base snapshot yet — the first build's capture is still running, capture failed, or no sandbox-capable host was available to produce one
- The snapshot is stale (the template was rebuilt since it was captured)
- The create requests a custom `disk_size_mb` — a resumed sandbox inherits the base snapshot's fixed-size overlay, so disk-size overrides always cold-boot (which sizes the writable overlay correctly)
- The resume itself fails at runtime (the fallback path)

Cold-boot fallback is transparent to the caller — the only difference is latency.

## Configuration

Base snapshots are captured automatically after every template build. Whether sandbox creation *resumes* from them is controlled by a server config flag:

```toml
[sandboxes]
  resume_from_base_snapshot = true
```

When disabled, sandboxes always cold-boot. Unlike the former warm pool, base snapshots consume only disk space on the producing host — no idle VMs, CPU, memory, or IP allocations are held in reserve.
