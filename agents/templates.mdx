An agent template selects the root filesystem that an agent VM boots from. Use one to preinstall operating-system packages, language libraries, fonts, scripts, and other static assets instead of uploading them at the start of every workspace.

<Warning>
Creating a template only builds an image. It does not apply that image to an agent. Set `--template` when you create the agent, or set `template` through the API. Runs and interactive sessions then inherit the template stored on the agent. Without one, the agent boots from the standard `agent-default` image.
</Warning>

## Start from the agent base image

Every custom agent Dockerfile must extend the ZWRM agent base image:

```dockerfile
FROM ghcr.io/zwrm-eu/agent-base:latest
```

The base image provides Ubuntu 22.04, Node.js 22, the `agent` user, SSH setup, the in-VM agent daemon, the ZWRM CLI, and the Pi, Claude Code, and Codex runtimes. Starting from a generic image such as `ubuntu`, `node`, or `python` omits that plumbing and can produce an image that builds successfully but cannot run as a ZWRM agent. You can inspect the image and its Dockerfiles in the public [`zwrm-eu/agent-images`](https://github.com/zwrm-eu/agent-images) repository.

Do not recreate the `agent` user or install the agent daemon yourself. ZWRM injects runtime configuration and platform credentials when the VM boots. Keep credentials out of the image and configure them as [agent secrets](/agents/secrets).

### Migrate from a generic Node image

If your Dockerfile begins like this:

```dockerfile
FROM node:22-slim
```

replace that base instead of rebuilding the agent environment from scratch:

```dockerfile
FROM ghcr.io/zwrm-eu/agent-base:latest

USER root
# Keep only the packages your workload adds to the ZWRM base.
RUN apt-get update && apt-get install -y --no-install-recommends YOUR_PACKAGES \
    && rm -rf /var/lib/apt/lists/*

USER agent
```

Node.js 22 is already present. Remove Dockerfile steps that create the `agent` user or reinstall Node.js, SSH, Pi, Claude Code, Codex, the ZWRM CLI, or `zwrm-agentd`.

Agent skills and images solve different problems. A skill gives the agent instructions and reusable scripts; the image supplies the operating-system packages and runtime environment those scripts need. Keep using skills for behavior, but bake their stable dependencies and large static assets into the custom image.

## Choose a build source

| Your assets are | Use |
|---|---|
| Private local files — scripts, fonts, models, and anything else next to your Dockerfile | A stored template created with `zwrm templates create`, which uploads your complete build context |
| A community template shared publicly | A public GitHub repository used directly as the agent template |

`zwrm templates create` uploads the complete Docker build context — the current directory by default, or the directory you pass with `--context`. `.dockerignore` is applied with standard Docker semantics, so `COPY` and `ADD` work with your local files exactly as in a local `docker build`. No Git repository is required, and your files stay private: the context is stored in the platform's object storage, scoped to your organization, and reused for every rebuild.

Keep three rules in mind:

- The compressed context may be up to 1 GiB. Individual files may be up to 1 GiB, and the extracted context up to 8 GiB.
- Without a `.dockerignore`, only `.git` is excluded — everything else below the context directory is uploaded and stored. Exclude secrets and build artifacts explicitly.
- `--dockerfile` must point to a file inside the context directory.

## Build the image

For an image with local assets, arrange a local directory like this:

```text
cowork-agent/
├── Dockerfile
├── .dockerignore
└── cowork/
    ├── .skills/
    ├── templates/
    └── scripts/
```

Then extend the agent base and add only your dependencies and content:

```dockerfile
FROM ghcr.io/zwrm-eu/agent-base:latest

USER root

RUN apt-get update && apt-get install -y --no-install-recommends \
    libreoffice-impress \
    python3 \
    python3-pip \
    && rm -rf /var/lib/apt/lists/*

RUN python3 -m pip install --no-cache-dir python-pptx

# Static defaults under /home/agent are seeded into each new workspace.
COPY --chown=agent:agent cowork/ /home/agent/cowork/

# A rootfs marker makes it easy to confirm which image booted.
RUN echo "cowork-1" > /etc/cowork-image-version

USER agent
WORKDIR /home/agent/cowork
```

Place files according to how they should behave at runtime:

| Content | Location | Behavior |
|---|---|---|
| System packages and immutable toolchains | `/usr/local` or `/opt` | Part of the image on every boot; does not enlarge each workspace volume |
| Editable starter files and per-workspace defaults | `/home/agent` | Seeded into a new workspace; later boots add missing files but preserve existing files |
| Customer inputs and generated outputs | `/home/agent` at runtime | Persisted in that workspace's volume |
| API keys and credentials | Agent secrets | Injected at boot; never stored in the image |

Large, read-only bundles generally belong in `/opt`. Put content in `/home/agent` only when the agent must edit it or when each workspace needs its own initial copy.

### Create the stored template

Run the create from the directory that contains the Dockerfile and assets, or pass `--context`:

```bash
cd cowork-agent
zwrm templates create cowork-base --dockerfile Dockerfile \
  --description "Cowork document tooling" \
  --disk-size-mb 4096

zwrm templates list
```

The CLI prints the directory it uploads and shows progress; a large context takes as long as your uplink allows. The build runs asynchronously. Wait until `cowork-base` is `ready` before assigning it to an agent, then use the stored name or ID as the agent's template.

<Note>
Size the writable disk for your assets: the default quota is 2048 MiB, and a large baked-in bundle on top of the agent base image can exceed it. Pass a larger `--disk-size-mb` at create time.
</Note>

### Public GitHub repository

For a community template you want to share, push the same layout to public GitHub and use it directly:

```text
github.com/acme/cowork-agent
```

You can also point to a subdirectory that contains the Dockerfile:

```text
github.com/acme/agent-images/cowork
```

ZWRM clones that repository, uses the selected directory as the Docker build context, and caches the result by repository commit. There is no separate `zwrm templates create` step for this path; the first agent boot builds the image.

## Attach the image to an agent

The template belongs on the agent definition, not on an individual run or session.

<Tabs>
  <Tab title="CLI">
    Create an agent from a stored template:

    ```bash
    zwrm agent create cowork \
      --runtime zwrm \
      --template cowork-base
    ```

    Or use a public GitHub build context directly:

    ```bash
    zwrm agent create cowork \
      --runtime zwrm \
      --template github.com/acme/cowork-agent
    ```
  </Tab>
  <Tab title="API">
    The REST API calls the ZWRM runtime `pi`:

    ```bash
    curl --request POST "https://<platform>/v1/agents" \
      --header "Authorization: Bearer $ZWRM_API_TOKEN" \
      --header "X-Org-ID: $ZWRM_ORG_ID" \
      --header "Content-Type: application/json" \
      --data '{
        "instance": "cowork",
        "agent_type": "pi",
        "size": "performance-2x",
        "template": "github.com/acme/cowork-agent"
      }'
    ```

    Use `claude` or `codex` for the other runtimes. The response contains the agent ID.
  </Tab>
</Tabs>

<Note>
The first workspace boot for a template builds that template's agent image — for a large context this takes several minutes. Later boots reuse the cached image and start in seconds. Rebuilding or updating the template triggers one more slow first boot.
</Note>

Every subsequent connect, run, dashboard chat, and interactive session uses the stored image. A session request selects a workspace, not an image:

```bash
curl --request POST "https://<platform>/v1/agents/$AGENT_ID/sessions" \
  --header "Authorization: Bearer $ZWRM_API_TOKEN" \
  --header "X-Org-ID: $ZWRM_ORG_ID" \
  --header "Content-Type: application/json" \
  --data '{"session_key":"customer-123"}'
```

The same `session_key` resumes the same workspace. A new key creates an independent volume and seeds it from the agent image. See [Interactive sessions](/agents/interactive#chat) for workspace-key behavior.

### Change an existing agent

Stop the agent VM while preserving its workspace volumes:

```bash
zwrm agent destroy cowork
```

The current CLI does not expose a template flag on `zwrm agent update`. Use the connect endpoint once to replace the stored template and boot the agent:

```bash
curl --request POST "https://<platform>/v1/agents/connect" \
  --header "Authorization: Bearer $ZWRM_API_TOKEN" \
  --header "X-Org-ID: $ZWRM_ORG_ID" \
  --header "Content-Type: application/json" \
  --data '{
    "instance": "cowork",
    "agent_type": "pi",
    "template": "github.com/acme/cowork-agent"
  }'
```

Use the existing agent's `agent_type`; the API rejects a runtime mismatch. Destroying an agent VM keeps its workspace volumes. Deleting the agent removes them.

## Verify the image

First confirm that the agent has a non-empty template:

```bash
zwrm agent list
```

Then boot the agent and inspect a marker or installed tool:

```bash
zwrm agent ssh cowork
cat /etc/cowork-image-version
test -d /home/agent/cowork/.skills
```

For a stored template, `zwrm templates list` must also report `ready`.

## Update the image

- For a stored template, `zwrm templates rebuild <name>` rebuilds from the stored context — for example after an agent-base update. To change the context files themselves, delete the template and create it again with the new directory, then re-attach agents that referenced it.
- For a GitHub template, push a new commit to the referenced repository.
- Stop the running agent VM before the next boot so it can use the rebuilt root filesystem.

Workspace volumes survive image changes. On boot, ZWRM copies files from the image's `/home/agent` skeleton only when the destination path does not already exist. Use a new `session_key` to test a pristine workspace. If an image update must always replace an asset, keep that asset in `/opt` or `/usr/local` instead of the persistent home directory.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| The agent still has the standard environment | The template was built but never assigned to the agent | Pass `--template` to `zwrm agent create`, or update the existing agent through `/v1/agents/connect` |
| `COPY` reports that a file does not exist | The file is outside the uploaded context or matched by `.dockerignore` | Run the create from the directory that contains it (or pass `--context`), and check `.dockerignore` |
| The upload is rejected with `413` | The compressed context exceeds 1 GiB | Trim it with `.dockerignore`, or download large assets during the build instead |
| The first chat or run after creating an agent takes minutes | The template's agent image builds on the first boot | Expected once per template; later boots start in seconds |
| SSH, chat, or the agent runtime does not start | The Dockerfile started from a generic base image | Start with `ghcr.io/zwrm-eu/agent-base:latest` |
| A changed file under `/home/agent` still has its old content | The workspace volume preserves existing paths | Test with a new session key, or keep immutable content outside `/home/agent` |
| Startup performs hundreds of file uploads or receives `429` responses | Static tools and assets are being synchronized at runtime | Bake them into the image and upload only per-session inputs |
| Agent creation reports `Template is still building` | The stored template is not ready yet | Wait for `zwrm templates list` to show `ready` |
| GitHub clone fails | The repository needs credentials or uses an SSH URL | Use a public repository over HTTPS |

## VM sizes

| Preset family | Description |
|---|---|
| `shared-cpu-1x/2x/4x/…` | Share host CPU; lower cost and less memory |
| `performance-*` | Dedicated CPU |

The default agent size is `performance-2x`. Set a per-agent default with `zwrm agent update <agent> --size <preset>`, or override it per run with `zwrm agent run --agent <agent> --prompt <text> --size <preset>`.

<Warning>
Build workloads usually need `performance-2x` or larger. A 512 MB VM can run out of memory during a large build.
</Warning>
