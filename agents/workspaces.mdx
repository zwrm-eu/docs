A **workspace** is where an agent's execution state lives: a persistent volume plus a session-continuity key. The VM that runs on it is ephemeral — the workspace volume (files, cloned repos, conversation transcript) is what carries everything forward between runs, chats, and SSH sessions.

## Keyed vs anonymous

| | Keyed workspace | Anonymous workspace |
|---|---|---|
| Created by | `--session <key>` on a run, or a schedule's `--session-key` | A run without `--session` |
| Conversation | Continues across runs with the same key | One-shot; continue only via `zwrm agent run continue <run-id>` |
| TTL | Agent's configured TTL (default 30 days), refreshed on use | 72 hours |

Set the keyed-workspace TTL per agent:

```bash
zwrm agent update my-project --workspace-ttl 720h   # 0 = never expire
```

When a workspace expires, its volume is reclaimed with it. Continuing or running on a workspace refreshes the clock.

## Concurrency

One live session per workspace: runs on the same session key **serialize** — a run that arrives while the workspace is busy is requeued and retried until the slot frees — while runs on different workspaces execute in parallel. This makes a session key a safe serialization point: a schedule that updates the same report every morning can never trample itself. Strict submission order is not guaranteed, though: after you interrupt a run, a run submitted *after* the interrupt counts as your newest instruction and takes the slot ahead of runs that were already queued.

## Repos

There is no built-in repo concept. A repo is whatever the prompt (or a skill) clones onto the workspace volume. `gh` is pre-authenticated in every VM, so "clone acme/api and open a PR" just works — and the clone persists on the volume for the next run with the same key.

## Home volume

Each workspace gets a persistent home volume — **5 GB by default**, and **grow-only**. Resize it from the CLI — `zwrm agent resize --volume` targets only the agent's **default** workspace volume, and the workspace must be stopped and cold first (disconnect and let it settle):

```bash
zwrm agent resize my-project --volume 20GB
```

A resize is refused while the workspace is running, suspended, or waking, or while its filesystem is frozen behind a snapshot — disconnect the agent and let the workspace go cold, then resize.

## Files

- **Browse and download** workspace files via the dashboard, or via the API (`GET /v1/agents/{agent}/workspaces/{ref}/files/...`). This works **even when the VM is off** — a cold workspace's files are served read-only straight from the stored volume. **Uploads** (`PUT`) need a live VM.
- **Run deliverables** — files the agent stages in `~/outputs/` are snapshotted onto the run when it finalizes, so they remain available after the VM is gone.

## Lifecycle & tiers

A workspace is tiered automatically to save resources — **you never manage this by hand**; the next message, run, or connect wakes it and resumes the conversation. Defaults below are operator-tunable.

| State | Entered after | What's kept | Wake cost |
|-------|---------------|-------------|-----------|
| **Running** | In use | Everything, live | — |
| **Suspended** | ~15 min idle | Firecracker snapshot (no compute billed) | ~⅓ second, mid-turn |
| **Cold** | ~48 h suspended | Volume + files + conversation (snapshot dropped) | A few seconds (full boot) |
| **Archived** | ~30 days cold | Conversation only — **working files on the volume are deleted** | Full boot, conversation rehydrated into a fresh empty volume |

The **conversation survives every tier**; **working files survive until archive**. An execution's teardown never kills a VM you are SSH-ed into.
