Runs are honest about their lifecycle: when the final turn ends, the run completes and the VM is gone — an agent cannot poll or wake itself up. While a run is live it has a platform tool for waiting, two native surfaces for delivering results, and (when you attach one) connectors for reaching a human.

<Note>
The platform has **no messaging capability of its own** — no built-in inbox, no message channels, no `send_message` tool. Everything an agent sends to a human goes through an [MCP connector](/context/connectors). The run's result and its `~/outputs/` files are the platform's own delivery surfaces.
</Note>

## Waiting

- **`sleep(seconds)` / `sleep_until(timestamp)`** — the agent parks the run (max 6 hours). The VM is snapshotted while sleeping (zero compute) and resumes mid-turn with full state. For anything longer, the agent is instructed to finish with a handoff instead.

Waiting tools exist **only in autonomous [runs](/agents/runs)**. Interactive sessions — dashboard chat, the [OpenAI-compatible API](/agents/openai-api), SSH — don't get them: a live reader is already watching the conversation, so there is nothing to sleep through.

## Run outputs

When the final turn ends, a run delivers through exactly two native channels:

- **Result** — the final turn's text, shown in `zwrm agent run status` and on the run page.
- **Files** — anything the agent staged in `~/outputs/` is snapshotted onto the run at finalize. Every VM boots with `~/outputs/` created and the convention written into the agent's platform instructions, so agents stage user-facing files there without being told.

Plain assistant text from earlier turns stays in the session timeline; the **result** and the **files** are what carry a run's deliverables out.

## Reaching a human

There is no platform primitive for notifications, replies, or alerts. To reach someone outside the dashboard, attach a [connector](/context/connectors) with the right tool — email, Microsoft Teams, Slack, and so on — and the agent calls it like any other tool. The run preamble tells the agent this directly: if no such connector is available, it must say so in its result and must never claim it notified, messaged, or alerted anyone unless a connector call actually succeeded.

For a run started by a [Microsoft Teams trigger](/automations/triggers#microsoft-teams-triggers), the reply path is the Microsoft 365 connector: the agent posts back to the originating chat with a connector tool, and the run prompt carries the destination chat ID.

To watch runs and lifecycle events programmatically, subscribe to [outbound webhooks](/automations/outbound-webhooks) — `agent_run.completed`, `agent_run.failed`, and `agent_run.needs_attention` are delivered to your endpoint.

## Escalations

Connector tools attached with `--escalate` pause the run (`needs_attention`) until you approve or deny the tool call from the run page. The VM waits suspended at no cost. See [Connectors](/context/connectors) for details.
