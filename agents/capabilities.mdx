Every agent VM carries a platform token so the agent can run `zwrm` commands — deploy, read logs, create databases. Capabilities decide **which** of those the token is allowed to do.

## Default

An agent gets every capability except `destroy`. It can build, ship, and manage; it cannot irreversibly tear down an app, machine, database, or volume — that stays an explicit per-agent grant.

```bash
zwrm agent update my-project --allowed-scopes apps:read,deploy,logs:read
zwrm agent update my-project --allowed-scopes ""   # reset to the platform default
```

The dashboard's agent page has the same picker, with a *default* / *custom* / *none* toggle. Leaving an agent on the default means it tracks future platform defaults rather than freezing today's list.

## Available capabilities

Scopes are `resource:action` pairs, plus a few atomic verbs:

| Group | Scopes |
|-------|--------|
| Apps & deploy | `apps:read`, `deploy`, `scale` |
| Secrets | `secrets:read`, `secrets:write` |
| Databases | `postgres:read`, `postgres:write` |
| Volumes | `volumes:read`, `volumes:write` |
| Networking | `routes:write` |
| Observability | `logs:read` |
| Agent library | `agents:read`, `agents:write`, `skills:read`, `skills:write`, `memories:read`, `memories:write` |
| Automation | `schedules:read`, `schedules:write`, `triggers:read`, `triggers:write` |
| MCP gateway | `mcp:read`, `mcp:write` |
| Connectors | `connectors:read`, `connectors:write` |
| Account | `ssh`, `identity` |
| Teardown | `destroy` |

<Warning>
Only `destroy` — permanently deleting apps, machines, databases, and volumes — is off by default. Three write capabilities that **are** in the default set deserve attention:

- **`agents:write`** is deletion of the org's *other* agents, their workspaces and volumes included — a prompt-injected agent could tear down a colleague's workspace. Only the platform-managed org assistant is protected.
- **`connectors:write`** attaches [connectors](/context/connectors) to the agent's own sessions, and it can reach every enabled virtual server in the org — including connectors whose upstream credential lives at the gateway and was never meant to back this agent.
- **`mcp:write`** lets an agent add, edit, sync, and delete MCP upstreams and virtual servers — adding an upstream opens a new outbound channel through the gateway, and editing one can repoint its URL, sending the stored credential to the new destination.

Orgs running agents at mixed trust levels should narrow these away with `--allowed-scopes` on lower-trust agents.
</Warning>

`mcp:read` covers viewing upstreams, their tool catalogs, and virtual servers. OAuth grant management (connecting accounts on a per-user upstream) and scope discovery are never reachable with an agent token, whatever its scopes — consent stays a human step.

Transferring an app to another organization is not grantable at all: no agent or scoped token can move an app out of your org.

## Removing the token entirely

The narrowest setting is no boot token at all:

```bash
zwrm agent update my-project --disable-boot-token
zwrm agent update my-project --disable-boot-token=false   # restore it
```

In the dashboard this is the **None** option on the capabilities card; on the API it is the `boot_token_disabled` field (settable at create and via `PATCH`). With the token disabled, the VM boots without an in-VM `zwrm` login — the agent cannot call the platform at all. The gateway (inference) credential still mints, so the harness keeps its models.

- This is distinct from an empty `--allowed-scopes`, which resets to the platform **default** set — it does not remove the token.
- A stored custom scope set is preserved while the token is disabled and applies again when it is re-enabled.
- The change applies at the **next boot**. A credential minted before the change stays valid until the workspace VM is disconnected — run `zwrm agent destroy <name>` to disconnect and revoke the agent's recorded platform credentials immediately (the volume is preserved).

<Note>
The boot token is the in-VM `zwrm` CLI login. Sessions additionally receive their own short-lived per-session credential for gateway-managed connectors and session tools — disabling the boot token does not detach the agent's [connectors](/context/connectors).
</Note>

## What the agent sees

A call outside an agent's capabilities fails with `403 token is not authorized for this endpoint`. The platform instructions tell agents that a 403 here is a policy limit rather than a bug — they should report it and ask you to grant the capability, not retry or work around it.

Agent tokens are also **pinned to their agent and organization**: an agent's token only acts as that agent, inside its org.

<Note>
The pin confines agent-addressed routes. Org-level resources — the skill library, schedules, triggers, the MCP gateway — resolve their target from the request rather than the URL, so an agent granted `skills:write`, `schedules:write`, or `mcp:write` can manage those across its own organization, not just its own agent.
</Note>

## Scoped API tokens

The same vocabulary works for your own tokens, so a CI job or dashboard gets exactly the reach it needs:

```bash
zwrm auth tokens create --name ci --scopes apps:read,deploy --org acme --expiry 8760h
zwrm auth tokens create --name obs --scopes apps:read,logs:read --org acme
```

| Flag | Description |
|------|-------------|
| `--scopes` | Comma-separated `resource:action` list; omit for an unrestricted token |
| `--org` | Organization a scoped token is bound to (defaults to your target org) |
| `--expiry` | Duration, e.g. `8760h`; omit for no expiry |
| `--name` | Token label |

A scoped token is confined to its organization — it cannot reach another org even if you're a member. Unscoped tokens keep behaving as before, carrying your full access.

Audit log entries record which credential made each call, so a scoped token's activity is attributable to that token rather than just to you.
