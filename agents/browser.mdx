The **Browser** template gives an agent a Chromium browser and a 1280×800 virtual desktop inside its VM. The agent browses through the page structure, operates the desktop by screenshot, mouse, and keyboard, and you can watch the desktop live from the chat and take control at any time.

## Create a browser agent

In the dashboard, open **Agents** → **Set up agent**, and pick **Browser** under **Environment**.

From the CLI:

```bash
zwrm agent create researcher --runtime claude \
  --template github.com/zwrm-eu/templates/browser
```

Through the API, set `template` to `github.com/zwrm-eu/templates/browser` on [`POST /v1/agents`](/api-reference/agents#agents).

<Note>
Use `performance-2x` or larger. Chromium renders in software, without a GPU, and `shared-cpu-*` sizes are too slow for it. Trial plans allow `shared-cpu-*` sizes only, so a browser agent needs a paid plan to run well.
</Note>

## What the agent gets

Every session gets two tool sets, on every runtime (Claude, Codex, OpenCode, and the zwrm runtime):

| Tools | What they do | Use for |
|---|---|---|
| `browser` (`mcp__browser__*`) | Navigate, click, type, fill forms, read the page's accessibility snapshot, take screenshots, manage tabs. Built on [Playwright MCP](https://github.com/microsoft/playwright-mcp). | Almost all web tasks. Fast and reliable, because it works on the page structure. |
| `computer` (`mcp__computer__*`) | `screenshot`, `zoom`, `left_click`, `double_click`, `right_click`, `left_click_drag`, `mouse_move`, `scroll`, `type`, `key`, `hold_key`, `wait`, `cursor_position` | Desktop applications, canvas-heavy pages, and sites that resist automation |

The `computer` tools mirror Anthropic's computer-use toolset, and are ported from Anthropic's reference implementation. Coordinates are screenshot pixels on a 1280×800 display.

Both tool sets drive the **same browser window**. There is one browser, and it always runs visibly on the desktop: the agent opens a page with the `browser` tools, and uses the `computer` tools on that same window when it needs to work by sight. Every page the agent opens through its tools therefore shows in the live view. Only a script the agent writes and runs headless from its own shell would not. To start another graphical program, the agent runs it from its shell in the background with `DISPLAY=:99`, for example `DISPLAY=:99 xterm &`, so the shell isn't blocked until the program exits.

The browser profile persists in the workspace, under `~/.zwrm/browser/profile`, so logins and cookies survive between sessions. Snapshots and screenshots the browser tools save go to `~/.zwrm/browser/output`, capped at 100 MB.

## Watch the desktop live

Open a chat with the agent and select **Desktop** in the side panel. The view shows the agent's desktop as it works, view-only. If the desktop isn't running yet, select **Start desktop**.

The live view keeps the agent's VM awake while it is open and visible. It disconnects when you collapse it, and about a minute after you switch to another tab.

## Take control

Select **Take control** to use the desktop with your own mouse and keyboard, for example to accept a cookie dialog, sign in to a site, or solve a captcha. Select **Hand back to agent** when you're done.

While you have control:

- Only your input reaches the desktop. Other people watching stay view-only, and only one person can hold control at a time.
- The agent's `computer` tools refuse input and tell the agent to wait. Its screenshots keep working, so it can see what you did. Its next observation after you hand back tells it that control is back.
- Control returns to the agent on its own about 90 seconds after your browser closes or loses its connection, so a closed tab never locks the agent out.

<Warning>
Taking control pauses the agent's computer-use tools. It does not stop commands the agent runs in its own shell. Treat it as a way to work alongside the agent, not as a security boundary.
</Warning>

An organization admin viewing a member's private chat can watch the desktop but cannot start it or take control.

## Route sites through a proxy

Some sites refuse requests from datacenter IP addresses. Sites behind Akamai or Cloudflare bot protection often do: the browser then fails with errors such as "Access Denied", `ERR_HTTP2_PROTOCOL_ERROR`, or an endless "Just a moment…" check, while other sites load normally. Other sites, Google among them, misbehave behind a proxy. So the agent routes **per site**:

1. Give the agent a proxy, for example a static ISP proxy, with the agent secret `BROWSER_PROXY`:

   ```bash
   printf %s "http://user:pass@proxy.example.com:8080" \
     | zwrm agent secrets set BROWSER_PROXY --stdin --instance researcher
   ```

2. That's all. Every site goes direct by default. When a site blocks it, the agent switches that site to the proxy with its `network` tools (`proxy_status`, `use_proxy`, `use_direct`), reloads, and remembers the choice in the workspace. Sites known to refuse datacenter networks start on the proxy.

Details:

- A choice covers the domain and its subdomains, and the most specific rule wins. Choices persist across sessions and reboots, per workspace.
- The proxy's credentials never enter the VM. The host the VM runs on connects to the proxy for the browser, so neither the agent nor code it runs can read them.
- An organization's [network policy](/agents/network-policy) applies to the proxy route too. A site the policy blocks stays blocked either way, and the agent's `network` tools tell it so instead of switching routes.
- `http://` and `https://` proxies are accepted, with or without credentials. A value that isn't a proxy URL is ignored, and the agent browses without a proxy.
- The proxy applies from the workspace's next boot or wake.
- Only the browser routes per site. The agent's shell commands go direct.

For logged-in work, prefer a static IP over a rotating pool: a stable address keeps sessions valid and avoids "new sign-in location" checks. Some sites, typically premium retailers, also refuse well-known proxy networks; a proxy can't help with those.

## Security

- Web pages are untrusted input. A page can contain text written to steer the agent. Review what an agent did on sites where it holds credentials.
- The browser profile holds the sites' cookies and logins. Anyone with access to the workspace (SSH, the chat, the files) can use them.
- Nothing in the VM listens publicly: the live view travels through the platform, authenticated as you.

## Troubleshooting

**The live view is black.** The desktop is running but nothing is on it yet: the agent hasn't opened a page in this session. The browser appears on the desktop when the agent first uses its `browser` tools. On images built before October 2, 2026 the browser ran invisibly: restart the agent's workspace so it boots the current image.

**The desktop does not appear in the chat.** The agent was not created from the Browser template, or its workspace runs an image from before the live view existed. Check the agent's **Environment** in its settings, and restart the workspace.

**The agent will not continue after you hand back control.** Tell it in the chat that control is back. Current images report the hand-back to the agent automatically.
