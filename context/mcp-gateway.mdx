The MCP gateway gives your organization one place to manage MCP. You register **upstreams** (external MCP servers) once — with credentials and a synced tool catalog — then compose curated subsets into **virtual servers**, each exposed as a single standardized HTTP MCP endpoint. Instead of every developer maintaining their own `.mcp.json` with N tokens, the org manages upstreams centrally and hands out one endpoint per use case.

## Concepts

| Concept | What it is |
|---------|------------|
| **Upstream** | An org-registered connection to an external MCP server: URL, transport, encrypted credentials, synced tool catalog, health. |
| **Virtual server** | A curated composition: selected tools from one or more upstreams, served as one MCP endpoint. |
| **Endpoint** | `https://mcp.<domain>/{org}/{server}` — Streamable HTTP, authenticated with your ZWRM API key. |

## Upstreams

```bash
zwrm mcp upstream add github https://api.githubcopilot.com/mcp/ --bearer-token ghp_...
zwrm mcp upstream add internal https://mcp.internal.example.com --header "X-Api-Key: abc123"
zwrm mcp upstream add sentry https://mcp.sentry.dev/mcp --oauth
zwrm mcp upstream list
zwrm mcp upstream tools github
zwrm mcp upstream sync github
zwrm mcp upstream grants sentry
zwrm mcp upstream rm github [--force]
```

| Flag (`upstream add`) | Description |
|------|-------------|
| `--bearer-token` | Bearer token sent to the upstream |
| `--header "Name: value"` | Custom auth header (repeatable) |
| `--oauth` | Per-user OAuth sign-in — each member connects their own account |
| `--oauth-client-id` / `--oauth-client-secret` | OAuth client credentials |
| `--oauth-token-url` | Token endpoint (client-credentials flow) |
| `--oauth-scope` | Optional space-separated OAuth scopes |
| `--oauth-issuer` | Pin the authorization server for `--oauth` (requires `--oauth-client-id`) |
| `--transport` | `streamable-http` (default) or `sse` |
| `--allow-private` | Allow private/internal addresses (host-admin only) |

The auth flags are mutually exclusive — see [Connector identity](/context/credentials) for which to pick and how per-user accounts work.

In the dashboard, the gateway page has a **Quick connect** grid of branded cards that pre-fills the registration form so you only supply credentials. Some presets — including [Microsoft 365](/context/shared-connectors) — are platform-hosted servers you point at with your own OAuth app. The cards come from the connector catalog, `GET /v1/mcp/connectors`.

### Connected through zwrm's own app

**HubSpot**, **Google Analytics** and **Mailchimp** connect through an OAuth app zwrm registered with the provider, so there is nothing to register on your side:

1. An operator opens **Integrations** → **HubSpot** (or **Google Analytics**, **Mailchimp**) and clicks **Connect**. This makes the organization's shared `hubspot` (or `google-analytics`, `mailchimp`) connection.
2. Each member signs in with their own account on the integration's page, or with `zwrm mcp connect hubspot`. In HubSpot, they pick the HubSpot account to connect.
3. Agents act as whoever asks, and see what that person's account can see. Someone who hasn't signed in yet gets a sign-in link to pass on.

The connection belongs to its integration: you can change whose account it acts as, but not its address or credentials, and you remove it with **Disconnect** on the integration's page (`DELETE /v1/integrations/hubspot`, and likewise for `google-analytics` and `mailchimp`). The server can't also be added by its address (`409` with `error_code: app_connector`).

If your organization already had a shared connection by that name to the same server, made with its own app (a `hubspot` connection with its own HubSpot app, say), **Connect** takes it over after asking: every sign-in on it ends, and each member signs in again through zwrm's app.

<Note>
If a HubSpot account has HubSpot's **Sensitive Data** setting on, HubSpot's MCP server doesn't return activities (calls, emails, meetings, notes, tasks) or conversations. Some HubSpot write tools ask for confirmation before they write.
</Note>

**Mailchimp** runs on zwrm's own Mailchimp server, since Mailchimp offers none that zwrm can use. Its tools draft campaigns and set their content, send tests, and schedule or send campaigns. They add and update contacts with their tags and groups, archive contacts, and read audiences, segments, templates and campaign reports. The member's Mailchimp role (owner, admin, manager, author or viewer) limits what they can do. A campaign can be deleted only while it is a draft. Transactional email, customer journeys and deleting a contact for good aren't covered: archive or unsubscribe a contact instead.

<Note>
Mailchimp sign-ins don't expire. One lasts until the member removes zwrm's app from their Mailchimp account or leaves that account, and zwrm then asks them to sign in again. **Disconnect** removes the connection in zwrm, but not zwrm's app in Mailchimp.
</Note>

### Who may add servers

Any member adds connections and virtual servers of their own. A member's are private to them until they share them; a member adds connections from the catalog only. Operators may connect any server, from the catalog or not. An organization admin can limit operators to the catalog with the **custom tools** setting (`builders_may_add_custom_tools`, on by default; `PUT /v1/org/settings`). With it off:
- adding a server outside the catalog, or pointing an existing one at a new address, takes an admin or owner;
- an OAuth sign-in may only use an issuer the catalog lists for that server, so members' sign-ins can't be sent to another authorization server;
- operators get `403` with `error_code: custom_tools_disabled`.

Admins and owners may always add any server.

### Private and shared connectors

A connection or virtual server you make is **private** to you; share it with the organization, and take it back, whenever you like:

```bash
zwrm mcp upstream add linear https://mcp.linear.app/mcp --oauth            # private to you
zwrm mcp upstream add linear https://mcp.linear.app/mcp --oauth --share    # shared at once
zwrm mcp upstream share linear
zwrm mcp upstream unshare linear
zwrm mcp server share eng-tools
```

| | Private | Shared |
|---|---|---|
| Its owner | Uses, changes, shares and deletes it | Uses it, takes it back private and deletes it; changing how it connects takes the operator role |
| Other members | Don't see it | See and use it |
| Operators | Don't see it | Also change it |
| Org admins | See and delete it | Also take it back private and delete it |

- **The organization's connectors.** Connections and servers added before members could add their own belong to the organization: shared, with no owner, and they stay shared. Operators change and delete them, as before.
- **Where you add one decides who sees it.** The **Integrations** page adds a connector that's yours, private. The developer console and the admin dashboard's MCP gateway pages add the organization's connectors, shared at once.
- **Shared servers use shared connections.** A shared virtual server can only compose shared connections. A plain member's own servers compose only connections that need no login, where every member signs in with their own account, or their own: a connection that acts as one account (a stored key, or a sign-in that falls back to the agent's) is an operator's to route. A connection can't be taken back private while a shared connector, or another member's connector or agent, still uses it. A server can't be taken back private while another member's agent has it. The refusal names what everyone may see, and counts other members' private ones. Taking a connection back private signs out everyone else who connected an account to it, and the agents that aren't your own private ones.
- **Changing a shared connector.** Members attached a shared connector as it is, so only operators change how a shared connection connects (its address, sign-in or identity policy) or which tools a shared server composes. Its owner takes it back private first, or asks an operator. When the owner of a private connection points it at a new address, their connected account on it is dropped. When an operator points a member's shared connection at a new address, its stored credential must come again in the same request (`auth_type` with its fields), and every connected account on it is dropped.
- **Signing in uses the connection.** Connecting your account to a connection needs a connection you may use: yours, or a shared one. An admin who sees a member's private connection can't sign in through it.

Names stay unique across the organization: an upstream's or server's name is part of its address (`/{org}/{server}`).

### Scope-aware tool exposure

On a **connector-known** OAuth upstream — one the platform ships per-tool scope data for, currently the [Microsoft 365](/context/shared-connectors) connector — a selection of *all* tools exposes only the tools covered by the scope string you configured: a 320-tool upstream narrowed to the handful your scopes actually permit. Tools needing scopes you didn't request are hidden rather than surfaced only to fail at call time. Explicit tool selections are always exposed, even beyond the configured scopes.

This narrowing requires both the vendored scope data and a configured scope string. Generic OAuth upstreams — and connector-known ones with no scope configured — get no scope-based narrowing: a select-all composition exposes their full catalog.

- Credentials are encrypted at rest and **never returned by the API**.
- The tool catalog is synced on add, every 5 minutes, on demand (`sync`), and when the upstream signals a tool-list change. The cached catalog keeps serving even when the upstream is down.
- When a previously synced tool's description or schema changes, the gateway records a catalog-change audit event — a defense against tool-poisoning ("rug pull") attacks.
- `rm --force` removes an upstream even when virtual servers still reference it.

## Virtual servers

```bash
zwrm mcp server create github-tools \
  --upstream "github:list_issues,create_issue,get_pull_request" \
  --description "GitHub issue triage tools"
zwrm mcp server list
zwrm mcp server get github-tools
zwrm mcp server add-upstream github-tools --upstream "linear:list_issues" [--replace]
zwrm mcp server remove-upstream github-tools linear
zwrm mcp server rm github-tools
```

- `--upstream` is repeatable: `"name"` selects all of that upstream's tools, `"name:tool1,tool2"` selects a subset. Tool allowlists are the composition — build a read-only variant by selecting only read tools.
- `--description` is served as the MCP `instructions` for connecting clients.
- On a per-user OAuth upstream, a member acts as their own connected account, an agent in a chat as the member who started the chat, and an agent in an unattended run as its own — there is no per-attachment identity setting to configure. See [Connector identity](/context/credentials).
- `add-upstream` grows an existing composition (`--upstream` takes the same selection syntax as `create`; adding an upstream already in the composition is an error unless `--replace` overwrites its tool selection). `remove-upstream` drops one or more upstreams and their tools; removing the last upstream is refused — delete the server with `rm` instead.
- Tool names pass through unmodified unless two upstreams collide, in which case they are prefixed `{upstream}_{tool}`. A composition can also rename individual tools via `exposed_names` (upstream tool → exposed name, per upstream selection in the [API composition body](/api-reference/skills-mcp)) — an explicit exposed name always wins over pass-through and collision prefixing.
- `get` shows the endpoint, the exposed tool mapping, and any problems.

## Connecting clients

```bash
zwrm mcp install github-tools                 # config for Claude Code (default)
zwrm mcp install github-tools --client cursor
zwrm mcp install github-tools --all           # every supported client
```

Supported clients: `claude-code`, `claude-api`, `cursor`, `vscode`, `windsurf`, `goose`, `openai`, `openapi`, `custom-gpt`. Authentication is your ZWRM API key as a bearer token; any member of the org can connect to any of the org's virtual servers.

```bash
claude mcp add --transport http github-tools https://mcp.example.com/acme/github-tools \
  --header "Authorization: Bearer <your-zwrm-api-key>"
```

## REST / OpenAPI face

Every virtual server is also a plain REST API — same URL space, auth, curation, and audit as the MCP endpoint. This makes gateway tools usable from anything that speaks OpenAPI but not MCP: n8n, LangChain OpenAPI toolkits, generated SDKs, GPT Actions.

```bash
# OpenAPI 3.1 description (one POST per tool)
curl -s -H "Authorization: Bearer <zwrm-api-key>" \
  https://mcp.<domain>/<org>/<server>/openapi.json

# Invoke a tool — the JSON body is the tool's arguments
curl -s -X POST \
  -H "Authorization: Bearer <zwrm-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"query": "open issues"}' \
  https://mcp.<domain>/<org>/<server>/tools/<tool>
```

- Tool input/output schemas embed verbatim in the OpenAPI document — MCP tool schemas are JSON Schema 2020-12, OpenAPI 3.1's native dialect.
- Results are flattened for REST consumers: text content that parses as JSON is returned as JSON, binary content becomes a `data:` URI, a single content item is unwrapped. Add `?envelope=full` for the raw MCP `CallToolResult`.
- A tool that runs and reports an error returns `422` — an outcome the caller can act on, not a gateway failure.
- Argument bodies are capped at 1 MiB.

For **Custom GPTs** (`zwrm mcp install <server> --client custom-gpt`): fetch the OpenAPI schema with curl and paste it into the GPT editor's Actions configuration, with Bearer auth. The schema importer can't send headers — the `?token=<key>` URL form exists for import-by-URL, but it embeds your API key in the URL, so prefer curl-and-paste or use a key you can revoke.

Servers that hold one agent's own tools (see [Choose an agent's tools](/context/connectors#choose-an-agents-tools)) are left out of the server list (`?include_agent_owned=true` shows them, each with its `owner_agent_id`) and can't be changed or deleted here; change the agent's tools instead.

## Agents and the gateway

Agents consume virtual servers as [connectors](/context/connectors). The key property: **upstream credentials never enter the agent VM** — the VM holds only its session's short-lived, automatically renewed [identity](/agents/capabilities#how-an-agent-authenticates), and the gateway injects the real credentials upstream. Which identity those calls carry is the [connector identity](/context/credentials) policy.

Agents can also *manage* the gateway when granted the `mcp:read` / `mcp:write` [capabilities](/agents/capabilities): reading upstreams, tool catalogs, and virtual servers, or registering and composing them. `mcp:write` **is in the default scope set**, a deliberate platform decision — which means a default-scoped agent can register or repoint an upstream, opening a new outbound channel. Security-sensitive orgs should narrow `mcp:write` away per agent. OAuth grant management always stays a human consent step, unreachable from any agent.

## Security model

- Two strictly separated credential planes: client → gateway (ZWRM API keys) and gateway → upstream (org-managed credentials or vaulted per-principal grants). Tokens are never passed through in either direction.
- Upstream URLs are validated against private/internal address ranges (SSRF protection), with DNS re-resolution at dial time. The `--allow-private` escape hatch is host-admin only.
- Every proxied tool call is audited with tool, upstream, duration, and caller.

## The `zwrm mcp` stdio server

Separate from the gateway, `zwrm mcp` with no subcommand runs a local stdio MCP server that exposes your autonomous agent runs as tools (`get_agent_run`, `list_agent_runs`, `cancel_agent_run`) — useful for letting a local coding agent watch over your ZWRM runs:

```bash
claude mcp add zwrm-agents -- zwrm mcp
```
