Connectors give an agent tools from the [MCP gateway](/context/mcp-gateway). Attaching a virtual server to an agent makes its tools available in every session as `mcp__<server>__<tool>` — while the upstream credentials stay at the gateway.

## Manage connectors

```bash
zwrm agent connectors list my-project
zwrm agent connectors attach my-project github-tools
zwrm agent connectors attach my-project github-tools --escalate
zwrm agent connectors attach my-project github-tools --disabled
zwrm agent connectors detach my-project github-tools
zwrm agent connectors verify my-project github-tools
zwrm agent connectors copy new-agent --from my-project
```

| Command | Description |
|---------|-------------|
| `list` | Show attached servers with status (`active`, `disabled`, `server-disabled`), escalate flag, and description |
| `attach` | Attach a virtual server. `--disabled` attaches without enabling; `--escalate` requires human approval for the connector's tools during autonomous runs |
| `detach` | Remove the attachment |
| `verify` | Live-test the connector (initialize → tools/list against its upstream) |
| `copy --from <agent>` | Copy another agent's connectors with their enabled/escalate flags |

Disabling a virtual server at the gateway (`server-disabled`) is the org-wide kill switch — it overrides every agent's attachment.

## Escalations

Tools from a connector attached with `--escalate` pause the run when the agent tries to use them: the run enters `needs_attention` and waits — VM suspended, at no cost — until you approve or deny the call from the run page. Use this for connectors with side effects (payments, production changes, outbound communication).

## Credential isolation

Agent VMs run model-driven tool calls and arbitrary shell commands, so ZWRM never places upstream credentials inside them:

- The harness's MCP config holds only a local address inside the VM. The in-VM daemon forwards each call to the gateway with the session's short-lived [identity](/agents/capabilities#how-an-agent-authenticates), renewed automatically and dead as soon as the session ends.
- The gateway resolves the connector, injects the upstream credentials, and proxies the call.
- A prompt injection that reads the agent's MCP config finds only that local address, usable from inside the VM while the session lasts — never your GitHub/Slack/API tokens.

## Which account the agent acts as

For upstreams using per-user OAuth, the account depends on who the agent is working for:

- **In a chat**, the agent acts as the **connected account of the member who started the chat**. That member connects their own account once (`zwrm mcp connect <upstream>`, or from the dashboard).
- **In an unattended run** (a schedule, a trigger, `zwrm agent run`), the agent acts as **its own connected account** — never its owner's. Authorize the agent once (from its dashboard page, or `zwrm mcp connect <upstream> --agent <id>`).

Other upstreams use the org-shared credential. Which credential a call carries follows purely from the upstream's auth type and the caller; there is nothing to configure per attachment. See [Connector identity](/context/credentials).
