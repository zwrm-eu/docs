Connectors give an agent tools from the [MCP gateway](/context/mcp-gateway). Attaching a virtual server to an agent makes its tools available in every session as `mcp__<server>__<tool>` — while the upstream credentials stay at the gateway.

## Choose an agent's tools

The short way: say which tools of each connected integration the agent may use, and which of them ask first.

```bash
zwrm agent tools set finance ms365 --all --ask-first send-mail,reply-mail-message
zwrm agent tools set finance hubspot --tools search-objects,get-object
zwrm agent tools list finance
zwrm agent tools remove finance hubspot
```

| Flag (`set`) | Description |
|------|-------------|
| `--all` | Every tool the integration has, including tools it gains later (as long as none asks first) |
| `--tools` | The tools named |
| `--ask-first` | Tools that wait for a person's approval on unattended runs. A tool named only here is allowed too |

ZWRM keeps the virtual servers this takes on the agent's behalf: `<agent>-<integration>`, and `<agent>-<integration>-ask` for the tools that ask first. They belong to the agent:
- the server and connector commands refuse to change them;
- the gateway's server list leaves them out;
- they go when the agent is deleted.

`list` also shows servers you attached by hand that give the agent tools as well. With `--all` and some tools asking first, the agent gets the integration's other tools as they are now; a tool the integration adds later stays off until you pick it.

An agent may add tools to its own ask-first list but never take one off, and may not let a tool another ask-first connector covers run unattended. Setting tools also needs the `mcp:write` [capability](/agents/capabilities), because it composes servers.

## Manage connectors

```bash
zwrm agent connectors list my-project
zwrm agent connectors attach my-project github-tools
zwrm agent connectors attach my-project github-tools --escalate
zwrm agent connectors attach my-project github-tools --disabled
zwrm agent connectors detach my-project github-tools
zwrm agent connectors verify my-project github-tools
zwrm agent connectors copy new-agent --from my-project
```

| Command | Description |
|---------|-------------|
| `list` | Show attached servers with status (`active`, `disabled`, `server-disabled`), escalate flag, and description |
| `attach` | Attach a virtual server. `--disabled` attaches without enabling; `--escalate` requires human approval for the connector's tools during autonomous runs |
| `detach` | Remove the attachment |
| `verify` | Live-test the connector (initialize → tools/list against its upstream) |
| `copy --from <agent>` | Copy another agent's connectors with their enabled/escalate flags, and its own tools as the target's own |

Disabling a virtual server at the gateway (`server-disabled`) is the org-wide kill switch — it overrides every agent's attachment.

### Who may attach what

Attaching a connector to an agent takes the right to change the agent, and:

- **Your own connectors**, any time; a private one only to a private agent, since every member uses a shared agent's connectors.
- **A shared connector that needs no login, or where each member signs in with their own account** (per-user OAuth with the default *user* identity policy): any member.
- **A connector that acts as one account** (a stored key, or an account connected for the agent): operators and above, unless the connection is your own. This is decided per connection, so a virtual server of your own over the organization's stored key still takes an operator. A plain member gets `403` with `error_code: shared_login_needs_operator`, naming the connection. The rule holds for an attachment switched off too: it still shows to everyone who sees the agent, and can be switched on.

The agent's connectors (`GET /v1/agents/{id}/connectors`, and the agent page) say whose account each connection acts as: each member's own, or one shared login and its account. In a shared chat, connections act as the agent's account unless the chat's owner has one act as [whoever started the turn](/api-reference/runs-sessions#sharing-a-chat), for members who let the chat use their own sign-ins. In a chat shared with chosen members, the owner can also lend a connection their [own sign-in](/api-reference/runs-sessions#sharing-a-chat): calls that change something then wait for the owner's approval.

### Sharing an agent with connectors

Sharing an agent hands its connectors to every member. So:

- an agent with a **private** connector on it can't be shared, even switched off: share the connector first, or take it off;
- an agent whose connectors act as **one account** asks you to confirm (an account connected for the agent counts on any OAuth connection: it's what shared chats and runs act as): the share is a `409` with `error_code: agent_shared_logins` naming them, until you share again with `confirm_shared_logins: true` (`zwrm agent share <agent> --yes`, or **Share anyway** in the dashboard).

## Escalations

Tools from a connector attached with `--escalate` pause the run when the agent tries to use them: the run enters `needs_attention` and waits — VM suspended, at no cost — until you approve or deny the call from the run page. Use this for connectors with side effects (payments, production changes, outbound communication).

## Credential isolation

Agent VMs run model-driven tool calls and arbitrary shell commands, so ZWRM never places upstream credentials inside them:

- The harness's MCP config holds only a local address inside the VM. The in-VM daemon forwards each call to the gateway with the session's short-lived [identity](/agents/capabilities#how-an-agent-authenticates), renewed automatically and dead as soon as the session ends.
- The gateway resolves the connector, injects the upstream credentials, and proxies the call.
- A prompt injection that reads the agent's MCP config finds only that local address, usable from inside the VM while the session lasts — never your GitHub/Slack/API tokens.

## Which account the agent acts as

For upstreams using per-user OAuth, the account depends on who the agent is working for:

- **In a chat**, the agent acts as the **connected account of the member who started the chat**. That member connects their own account once (`zwrm mcp connect <upstream>`, or from the dashboard).
- **In an unattended run** (a schedule, a trigger, `zwrm agent run`), the agent acts as **its own connected account** — never its owner's. Authorize the agent once (from its dashboard page, or `zwrm mcp connect <upstream> --agent <id>`).

Other upstreams use the org-shared credential. Which credential a call carries follows purely from the upstream's auth type and the caller; there is nothing to configure per attachment. See [Connector identity](/context/credentials).
